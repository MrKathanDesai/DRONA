# RF v3 (experiment): everyday 2.4 GHz emitters, CNN, smoothing, timing features

v2 has only seen receiver noise and one lab's background as "no drone". v3 adds **simulated** Wi-Fi, microwave-oven and Bluetooth signals (`src/dronedet/data/rf_emitters.py`) as negatives: Wi-Fi and microwave in training, **Bluetooth held out** (test only), through both the DroneRF and Tampere pipelines. Same data, splits, 128 sub-band features and threshold rule (1% FPR on validation negatives) as v2. Generated by `scripts/train_rf_v3.py`. **v2 stays deployed**; this is an experiment.

The emitters are simple stand-ins, not standard-compliant waveforms, so the false-alarm rates below are indicative, not a measurement on real traffic. DroneRF's Bebop and AR are themselves Wi-Fi drones, so Wi-Fi is a hard negative on purpose.

## Same test set: v2 vs v3, forest vs 1D-CNN

Smoothed = alarm only when 3 of 5 consecutive windows of the same stream are hits. Synthetic windows are independent, so smoothing flatters them a little (real interference is correlated in time).

| model | PR-AUC | recall | FPR (false alarms) | recall, smoothed | FPR, smoothed |
|---|---|---|---|---|---|
| v2 forest | 0.994 | 0.993 | 0.105 (60/570) | 0.931 | 0.067 |
| v3 forest | 0.999 | 0.997 | 0.030 (17/570) | 0.931 | 0.002 |
| v3 1D-CNN | 0.705 | 1.000 | 0.200 (114/570) | 0.931 | 0.098 |

## Time-frequency features (raw Tampere IQ only)

Averaging a 25 ms window into one spectrum throws away timing: burst length, duty cycle, frequency hopping. Here 8 timing features per band (`rf_emitters.tf_features`, 6.4 us frames) are computed from raw samples. Only Tampere drones and synthetic negatives have raw samples here, so this is a separate, small experiment: each Tampere drone left out in turn, negatives = synthetic noise, Wi-Fi, microwave (train) plus held-out Bluetooth (test).

| features | mean recall, unseen drone | false alarms: noise | false alarms: wifi | false alarms: microwave | false alarms: bluetooth |
|---|---|---|---|---|---|
| PSD only | 1.000 | 0.000 | 0.280 | 0.008 | 1.000 |
| PSD + time-frequency | 0.996 | 0.000 | 0.256 | 0.024 | 1.000 |
| time-frequency only | 0.927 | 0.000 | 0.004 | 0.000 | 1.000 |

## Reading the results

- **Emitter negatives help.** v2 calls many simulated Wi-Fi / microwave windows "drone"; v3 brings overall false alarms from 0.105 to 0.030 with no loss of drone recall (0.997).
- **Bluetooth (never trained on) is the weak spot.** The v3 forest calls 10-20% of it "drone"; the CNN and the Tampere-only timing experiment call nearly all of it "drone". Its 1 MHz frequency hopping looks like a drone control link. Real Bluetooth recordings in training are the fix.
- **Smoothing** (3 of 5) cuts v3's false alarms to 0.002; the first windows of each stream can never alarm, so recall drops to 0.931.
- **Forest beats the 1D-CNN** (PR-AUC 0.999 vs 0.705): with a few thousand windows the small CNN overfits to receiver details (it calls held-out pink noise on the Tampere pipeline "drone").
- **Timing features are the useful part for Wi-Fi:** alone they take Wi-Fi false alarms from 0.280 (spectrum only) to 0.004, at some cost in recall on unseen drones. Simply appending them to the 128 spectrum features barely changes the forest; weighting or selecting them is future work.

## Limits

- All non-drone emitters are simulated; a real-traffic false-alarm rate needs recordings such as CardRF or DroneDetect.
- DroneRF has no raw samples cached, so the timing features are tested on Tampere (anechoic chamber) only.
